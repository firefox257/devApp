# SMALL LANGUAGE (SL) COMPILER DOCUMENTATION
## 0. Documentation Notes
In the documentation, never use three backticks. This confuses front-end AIs and makes them think it is the end of a code block.
## 1. OVERVIEW
Small Language (SL) is a lightweight, high-performance programming language with C++-like syntax. It emphasizes explicit memory management, predictable data layout, and a strict separation between data structures (classes) and behavior (functions).
### 1.1 COMMENTS
Comments are used to document code and are ignored by the compiler.
- Single-line comments start with `//`
// This is a single-line comment
- Multi-line comments are enclosed in `/*` and `*/`
/*
This is a
multi-line comment
*/
## 2. PRIMITIVE TYPES
SL provides a strict set of primitive types with guaranteed sizes.
Type      Description                     Size
----      -----------                     ----
void      No type / empty                 -
bool      Boolean value (true or false)   1 byte
char      Single character                1 byte
int8      8-bit signed integer            1 byte
int16     16-bit signed integer           2 bytes
int32     32-bit signed integer           4 bytes
int64     64-bit signed integer           8 bytes
uint8     8-bit unsigned integer          1 byte
uint16    16-bit unsigned integer         2 bytes
uint32    32-bit unsigned integer         4 bytes
uint64    64-bit unsigned integer         8 bytes
float32   32-bit floating-point number    4 bytes
float64   64-bit floating-point number    8 bytes
Pointer Types:
Any primitive type can be suffixed with `*` to denote a pointer (memory address):
void*, bool*, char*, int8*, int16*, int32*, int64*, uint8*, uint16*, uint32*, uint64*, float32*, float64*
Note: For pointer-sized arithmetic or sizes, `uint64` is used universally to maintain cross-platform consistency (e.g., between 32-bit and 64-bit targets).
### 2.1 Characters and Strings
- Character Definition:
char c = 'a';
(Must be exactly one character. Using multiple characters like `char c = 'ab';` will result in a compiler error. Single quotes are strictly reserved for `char`).
- String Definition:
Strings (both single-line and multi-line) are enclosed in double quotes (`"`):
"This is a single-line string"
"
This is a
multi-line string
"
- String Interpolation:
Variables can be embedded directly into double-quoted strings using the `${}` syntax:
int32 age = 25;
print("Age is ${age}"); // Outputs: Age is 25
### 2.2 Escape Characters
The following escape characters are supported within character and string literals:
\n  : Newline
\t  : Horizontal tab
\r  : Carriage return
\\  : Backslash
\'  : Single quote
\"  : Double quote
\$  : Literal dollar sign
\${ : Literal dollar sign and brace (prevents string interpolation)
\0  : Null character (NUL)
\b  : Backspace
\f  : Form feed
\a  : Alert / Bell
\v  : Vertical tab
\xHH: Hexadecimal character code (e.g., \x41 for 'A')
\ooo: Octal character code (e.g., \101 for 'A')
### 2.3 Type Qualifiers (const, volatile, atomic)
Type qualifiers enforce specific memory access patterns and immutability rules.
// 1. Constant variable (read-only immutability)
const int32 MAX_SIZE = 100;
// 2. Pointer to constant data (data cannot be modified)
const char* str = "hello";
// 3. Constant pointer (pointer address cannot be modified)
const int32* ptr = &some_int;
// 4. Const parameter in functions
void printValue(const int32* value) {
// *value = 5; // Error: cannot modify a const object
}
// 5. Const explicit 'this' pointer (read-only method)
public int32 try1::getValue(const try1* this) {
// this->x = 10; // Error: cannot modify member via const this pointer
return this->x;
}
// 6. Volatile variable (prevents compiler optimization, essential for hardware registers)
volatile int32* hardwareRegister = (int32*)0x40021000;
// 7. Atomic variable (ensures thread-safe, indivisible read-modify-write operations)
atomic int32 counter = 0;
atomic bool is_ready = false;
## 3. OPERATORS
SL supports a comprehensive set of C++-style operators, categorized by function:
### 3.1 Arithmetic Operators
+   : Addition (also unary plus)
-   : Subtraction (also unary minus/negation)
*   : Multiplication
/   : Division
%   : Modulo (remainder)
++  : Increment (prefix or postfix)
--  : Decrement (prefix or postfix)
### 3.2 Relational / Comparison Operators
==  : Equal to
!=  : Not equal to
>   : Greater than
<   : Less than
>=  : Greater than or equal to
<=  : Less than or equal to
### 3.3 Logical Operators
&&  : Logical AND
||  : Logical OR
!   : Logical NOT
### 3.4 Bitwise Operators
&   : Bitwise AND
|   : Bitwise OR
^   : Bitwise XOR (exclusive OR)
~   : Bitwise NOT (One's complement)
<<  : Bitwise Left Shift
>>  : Bitwise Right Shift
### 3.5 Assignment Operators
=   : Simple assignment
+=  : Add and assign
-=  : Subtract and assign
*=  : Multiply and assign
/=  : Divide and assign
%=  : Modulo and assign
&=  : Bitwise AND and assign
|=  : Bitwise OR and assign
^=  : Bitwise XOR and assign
<<= : Bitwise Left Shift and assign
>>= : Bitwise Right Shift and assign
### 3.6 Member and Pointer Access Operators
.   : Member access (dot operator)
->  : Member access via pointer (arrow operator)
.*  : Pointer-to-member access (via object)
->* : Pointer-to-member access (via pointer)
*   : Dereference (access value at address)
&   : Address-of (get memory address)
### 3.7 Miscellaneous / Special Operators
?:     : Ternary / Conditional operator (condition ? expr1 : expr2)
,      : Comma operator
::     : Scope resolution operator
()     : Function call operator / Type casting / Initialization
[]     : Subscript / Array indexing operator
sizeof : Returns the size (in bytes) of a type or object.
sizeof(int32);       // is 4
sizeof(int64);       // is 8
int32 x; sizeof(x);  // is 4
class try1 { private: char c; public: int32 x; };
sizeof(try1);        // is 8 (natural alignment, 3 bytes of padding)
class try2 { private: char c; public: int32 x; } __attribute__((packed));
sizeof(try2);        // is 5 (packed)
int32 array[3]; sizeof(array); // is 12
typeof : Compile-time type introspection operator. typeof(expr) or typeof(Type)
evaluates to the type's name as a const char* string.
hashtype : Compile-time type hash operator. hashtype(expr) or hashtype(Type)
evaluates to the uint64 hash of the type's fully-qualified name
(see Section 23). A result of 0 means the type is unknown or could
not be resolved.
int32 x;
const char* name = typeof(x);   // "int32", usable for printing
uint64 h = hashtype(x);         // hash of "int32"
Comparisons: Note that comparing two const char* values with == compares their
memory addresses, not their string contents. To compare type names as strings,
use a string comparison function like cmpstr(typeof(x), "int32"). For zero-cost
compile-time type checking, use the hashtype operator (e.g., hashtype(x) == hashtype(int32))
or the match type construct.
if (hashtype(x) == hashtype(int32)) { } // explicit hash compare
Pointer types and class types work the same way:
classname* cptr;
if (hashtype(cptr) == hashtype(classname*)) { }
Every type, including every class, has a compile-time hash.
## 4. FUNCTIONS
Functions are defined with a return type, name, and parameter list.
Standard Function Example:
int32 strlen(char* str) {
	int16 i = 0;
	while (str[i] != 0) {
		i++;
	}
	return i;
}
## 5. CLASSES AND STRUCTS
Classes in SL define data layout only. By default, the compiler lays out members with normal alignment and padding for performance. For a predictable, padding-free layout (networking, serialization, file I/O), opt in explicitly with __attribute__((packed)) (see 5.2.1).
### 5.1 Class Definition Rules
1. No Inline Functions: Classes cannot have functions defined inside the class body. All methods must be defined externally.
2. Access Modifiers: `public`, `protected`, and `private` are supported for both data members and class functions.
3. Inheritance: Supports `public`, `protected`, and `private` inheritance.
### 5.2 Class Declaration Syntax
class classname : public classname2 {
	public:
	int32 x;
	protected:
	// protected members
	private:
	// private members
};
### 5.2.1 Packed Alignment (Opt-In)
Packing is never implicit. To get a packed layout with no padding, declare it explicitly:
class classname {
	int8 a;
	int32 b;
} __attribute__((packed));
Without the attribute, members are aligned to their natural alignment and the compiler may insert padding between members and at the end of the class.
Note: `atomic` types (see Section 24) require natural alignment for hardware and WebAssembly compatibility. The compiler will emit a hard error if an `atomic` type is placed inside a `__attribute__((packed))` struct or cast to an unaligned pointer.
### 5.3 Flexible Out-of-Line Method Definitions
Functions belonging to a class are defined flexibly anywhere in the code using the scope resolution operator `::`.
The `this` pointer must be explicitly declared as the first parameter.
Access modifiers (`public`, `protected`, `private`) must be stated in the definition if they apply.
// Regular method with access modifier
public void classname::func(classname* this, int32 i) {
	this->x = i;
}
// Constructor (explicit this pointer)
classname::classname(classname* this) {
	// Constructor logic
}
// Destructor (explicit this pointer)
classname::~classname(classname* this) {
	// Destructor logic
}
### 5.3.1 Constructor Initializer Lists
SL supports C++-style constructor initializer lists, which are evaluated immediately after memory allocation but before the constructor body executes. This mechanism is strictly required for initializing `const` members, reference (`&`) members, and base class subobjects, as these cannot be legally assigned to after construction has begun.
[CODE]
class MyClass {
	public:
	const int32 id;
	int32& refValue;
	int32 normalValue;
};
// Constructor using an initializer list
MyClass::MyClass(MyClass* this, int32 initId, int32& initRef, int32 initNormal)
: id(initId), refValue(initRef), normalValue(initNormal) {
	// Constructor body executes AFTER all members in the initializer list are initialized.
	// 'id' and 'refValue' cannot be assigned here; they must be in the initializer list.
}
[/CODE]
Rules for Initializer Lists:
1. Syntax: The initializer list follows the parameter list and is preceded by a colon (:).
2. Separation: Multiple members are separated by commas (,).
3. Initialization Order: Members are initialized in the exact order they are declared in the class definition, not the order they appear in the initializer list. The compiler will emit a warning if the initializer list order does not match the declaration order to prevent subtle dependency bugs.
4. Fallback Initialization: If a member is omitted from the initializer list, the compiler checks if it has a default member initializer defined in the class body (see Section 17.3). If a default value exists, it is used. If no default initializer is provided, the member is NOT automatically zero-initialized; it retains whatever raw data already exists in the allocated memory. It is strictly the developer's responsibility to ensure all members are properly initialized.
5. Explicit `this`: The explicit `this` pointer remains the first parameter of the constructor signature, but it is not included in the initializer list itself.
6. Base Class Initialization: Base class constructors and destructors are automatically invoked by the compiler in the correct order, similar to C++. Developers do not need to explicitly call base class constructors or destructors in the initializer list or method body.
### 5.4 Static Constructors and Destructors
SL supports module-level static initialization and teardown for classes.
// Static constructor: Runs once at application startup, before main()
static classname::classname() {
// Global initialization logic
}
// Static destructor: Runs once when the application closes
static classname::~classname() {
// Global cleanup logic
}
### 5.5 Operator Overloading
SL supports operator overloading for classes. Operators are defined similarly to methods, using the `operator` keyword followed by the symbol being overloaded. The explicit `this` pointer is always the first parameter. Access modifiers can be applied.
Supported Overloadable Operators:
- Arithmetic: +, -, *, /, %, ++, --
- Relational: ==, !=, <, >, <=, >=
- Bitwise: &, |, ^, ~, <<, >>
- Assignment: =, +=, -=, *=, /=, %=, &=, |=, ^=, <<=, >>=
- Access/Call: [], (), ->, .*, ->*
Examples:
// Overloading the array subscript operator []
public classname& classname::operator[](classname* this, int32 index) {
// Return reference to element at index
}
// Overloading the addition operator +
public classname classname::operator+(classname* this, classname& other) {
// Addition logic
}
### 5.6 Instantiation and Method Calls
When a method is called using dot notation (`.`), the compiler automatically passes the object's address as the explicit `this` parameter, providing clean syntax while maintaining C-style ABI compatibility.
classname n1;
n1.func(123); // Compiler translates this to: classname::func(&n1, 123);
### 5.7 Abstract Classes and Polymorphism
SL supports abstract class patterns by allowing method declarations without definitions. The compiler will not error on a missing definition as long as the method is not invoked on an instance of that exact base class. To use the functionality, a derived class must implement the method.
class tryabstract {
	public:
	int32 x;
};
// Declaration only (acts as an abstract method). No compiler error here.
// Errors only if it is trying to be called on the base class directly.
public int32 tryabstract::getX(tryabstract* this);
// Derived class implementing the method
class imptry : public tryabstract {
};
public int32 imptry::getX(imptry* this) {
	return this->x;
}
// --- VALID USAGE ---
// 1. Instantiating derived class and calling the method
imptry it;
print(it.getX());
// 2. Polymorphic usage via pointer (requires virtual keyword for dynamic dispatch, see Section 17.2)
tryabstract* at = new imptry();
print(at->getX());
// --- INVALID USAGE ---
// 3. Instantiating base class and calling unimplemented method will result in an error
// tryabstract at;
// print(at.getX()); // Error: getX is not implemented for tryabstract
### 5.8 Friend Invocation (`friendclass`)
SL supports a `friendclass` qualifier that allows a class method to be invoked using dot notation or operator syntax on an instance of a *different* class. This acts as an "extension method" or "invocation binding," allowing clean, object-oriented syntax for operations that logically involve two different classes, without polluting the target class with inline methods.
Because all functions in SL are defined out-of-line (outside the class brackets), the compiler requires explicit access modifiers (`public`, `protected`, or `private`) at the beginning of the function definition.
#### 5.8.1 Syntax and Access Rules
The `friendclass` qualifier is appended to the end of a class method's signature. It specifies which external class this method can be invoked upon.
**Crucial Access & Invocation Rules**:
1. **Explicit Access Modifier**: The function must begin with `public`, `protected`, or `private` to define its visibility.
2. **Ownership**: The function physically belongs to the class it is defined in (the "owner" class). It has full access to the owner class's `private` and `protected` members via the explicit `this` pointer.
3. **Friend Access**: The class specified in `friendclass` (the "friend" class) is strictly restricted to **public** members only. The function does *not* gain private/protected access to the friend class.
4. **Invocation Binding**: The method can be called using dot notation on an instance of the friend class. The compiler automatically maps the friend class instance to the corresponding parameter.
[CODE]
// Basic syntax
access_modifier return_type OwnerClass::method_name(OwnerClass* this, FriendClass* obj) friendclass FriendClass;
[/CODE]
#### 5.8.2 Examples of Usage
**Example 1: Basic Method Invocation**
In this example, `myfunc` belongs to `class1`. It can access `class1`'s private members. However, because it is bound to `class2` via `friendclass`, it can be invoked on `class2` instances using dot notation, but it can only access `class2`'s public members.
[CODE]
class class1 {
	private:
	int32 secret;
	public:
	int32 publicData;
};
class1::class1(class1* this) {
	this->secret = 42;
	this->publicData = 0;
}
class class2 {
	public:
	int32 publicVal;
	private:
	int32 privateVal;
};
// 'myfunc' belongs to class1. It is bound to class2 for invocation.
// Notice the explicit 'public' modifier at the front.
public void class1::myfunc(class1* this, class2* cl2) friendclass class2 {
	// ALLOWED: 'this' is class1, so we can access its private members
	print("class1 secret: ${this->secret}");
	// ALLOWED: 'cl2' is class2, and publicVal is public
	this->publicData = cl2->publicVal;
	// COMPILER ERROR: 'cl2' is class2, but privateVal is private.
	// friendclass does NOT grant private access to the friend class.
	// cl2->privateVal = 10;
}
int32 main() {
	class1 c1;
	class2 c2;
	c2.publicVal = 100;
	// Valid invocation: Called on c2 (the friend class), passing c1 (the owner).
	// The compiler translates this to: class1::myfunc(&c1, &c2);
	c2.myfunc(c1);
	// Also valid via explicit scope resolution:
	class1::myfunc(&c1, &c2);
	return 0;
}
[/CODE]
**Example 2: Operator Overloading and Chaining**
`friendclass` is exceptionally useful for operator overloading, allowing you to define how an external class interacts with your class using standard operators, while keeping the logic inside the owner class.
[CODE]
class Stream {
	public:
};
Stream::Stream(Stream* this) {}
class Logger {
	private:
	int32 level;
	public:
};
Logger::Logger(Logger* this) {
	this->level = 1;
}
// 'operator<<' belongs to Logger. It is bound to Stream for invocation.
// It returns a reference to the Stream to allow chaining.
public Stream& Logger::operator<<(Logger* this, Stream& strm) friendclass Stream {
	// Can access Logger's private 'level'
	print("Logging to stream at level ${this->level}");
	return strm;
}
int32 main() {
	Stream s;
	Logger log;
	// Invokes Logger::operator<<.
	// 'strm' is bound to 's', and 'this' is bound to 'log'.
	// Because it returns Stream&, we can chain operations.
	s << log;
	return 0;
}
[/CODE]
#### 5.8.3 Key Design Benefits
1. **Pure Data Schemas**: Keeps class definitions clean. You don't need to write boilerplate wrapper methods inside the friend class just to expose functionality that actually belongs to the owner class.
2. **Safe Encapsulation**: Unlike C++ `friend` declarations, this mechanism does *not* break encapsulation. The function only gets public access to the friend class, ensuring private data remains secure.
3. **Ergonomic Syntax**: Enables natural dot-notation (`c2.myfunc(c1)`) and operator chaining (`s << log`) for cross-class operations, improving code readability.
4. **Zero-Cost ABI**: Under the hood, this is just a standard function call. The compiler simply reorders the arguments to match the explicit `this` and friend parameters, maintaining perfect C-ABI and WebAssembly compatibility.
### 5.9 Properties (Getters and Setters)
SL supports a clean, explicit property syntax that allows developers to use natural dot-notation for access and assignment, while routing the operations through dedicated getter and setter methods. This enforces encapsulation without sacrificing ergonomic syntax.
#### 5.9.1 Naming Convention
To define a property named `PropertyName`, the developer defines out-of-line methods using the `get:` or `set:` prefix followed by the property name:
- Getter: `get:PropertyName`
- Setter: `set:PropertyName`
When the compiler encounters dot-notation access (e.g., `object.PropertyName`), it automatically translates it to the corresponding `get:` or `set:` method call, passing the explicit `this` pointer.
#### 5.9.2 Syntax and Rules
1. **Getter Signature**: Must return the property type and take a `const ClassName* this` pointer to guarantee read-only access.
2. **Setter Signature**: Must return `void` (or the class reference for chaining), take a mutable `ClassName* this` pointer, and accept the new value as the second parameter.
3. **Encapsulation Override**: If `get:` or `set:` methods are defined for a name, dot-notation access to that name will *always* route to these methods, even if a public member with the same name exists. It is best practice to keep the underlying storage `private` or `protected`.
4. **Read-Only / Write-Only**: Defining only `get:` makes the property read-only. Defining only `set:` makes it write-only.
#### 5.9.3 Example Implementation
[CODE]
class Player {
private:
char* _name;      // Internal storage (hidden)
int32 _health;    // Internal storage (hidden)
public:
Player(Player* this);
};
Player::Player(Player* this) {
this->_name = "Unknown";
this->_health = 100;
}
// --- GETTER ---
// The 'const' this pointer ensures this method cannot modify the object.
public const char* Player::get:Name(const Player* this) {
return this->_name;
}
// --- SETTER ---
// Allows validation or side-effects before assignment.
public void Player::set:Name(Player* this, const char* newName) {
if (newName != null) {
this->_name = newName;
}
}
// --- READ-ONLY PROPERTY EXAMPLE ---
public int32 Player::get:Health(const Player* this) {
return this->_health;
}
// Note: No set:Health is defined, making Health read-only.
int32 main() {
Player player;
// 1. Getter Invocation
// Compiler translates: player.Name  -->  Player::get:Name(&player)
const char* name = player.Name;
print("Player name is: ${name}");
// 2. Setter Invocation
// Compiler translates: player.Name = "Hero"  -->  Player::set:Name(&player, "Hero")
player.Name = "Hero";
// 3. Read-Only Property
int32 hp = player.Health; // Translates to Player::get:Health(&player)
// player.Health = 50;     // COMPILER ERROR: No set:Health method exists
return 0;
}
[/CODE]
#### 5.9.4 Compiler Implementation Notes
- **AST Transformation**: During the semantic analysis phase, the compiler detects member access (`.`) or member assignment (`.` followed by `=`). If a matching `get:` or `set:` method exists in the class scope, the AST node is rewritten into a standard function call node.
- **Zero-Cost ABI**: This is purely syntactic sugar. The generated asm.js code is identical to a direct function call. There is no hidden proxy object or runtime reflection overhead.
- **Chaining Support**: Setters can optionally return `ClassName&` (or `ClassName*`) to allow method chaining, though `void` is the standard recommendation for simple property assignment.
## 6. MODULES AND EXPORTING
To make functions or class methods visible to other compilation units, dynamic libraries, or external linkers, use the `export` keyword.
### 6.1 Exporting with Definition
export void func() { // The export name is "func"
// Function body
}
// Note: The exported name will naturally be classname::func
export void classname::func() { // The export name is "classname::func"
// Method body
}
// Alternative Names: You can define an alternative exported name using parentheses
export(othername) void func() { // The export name is "othername"
// Function body exported as "othername"
}
export(CustomInit) static classname::classname() { // The export name is "CustomInit"
// Static constructor exported as "CustomInit"
}
### 6.2 Forward Export (Declaration Only)
You can also export a function or method by declaration alone, allowing the definition to remain internal or be resolved at link time.
export func;
export classname::func;
export(AliasName) func;
### 6.3 Export Class
export class classname {
private:
int32 _id;
public:
int16 x;
int16 y;
};
public void classname::printout(char* str) {
print(str);
}
// All the classname public members and public functions are exported.
// export "classname::_id" is not visible since it is private.
// export "classname::x" is visible.
// export "classname::y" is visible.
// export "classname::printout" is visible.
export(tryclass) class classname {};
void classname::func() {};
// export "tryclass::func" is visible.
### 6.4 How Exports and Imports are Used
Imports are used to include only what is exported from a file, effectively managing the global namespace.
// In file1.sl
int32 x = 123; // Not exported, remains internal
export int32 func1() {
return x;
}
void func2() { // Not exported, remains internal
}
// In file2.sl
#import "file1.sl"
// func1 is available.
// x is NOT available.
// func2 is NOT available.
// Contrast with #include:
// #include "file1.sl"
// func1, func2, and x are ALL available.
## 7. TEMPLATES
SL supports generics through templates, allowing functions and classes to operate with generic types.
### 7.1 Function Templates
Functions can be templated by declaring template parameters before the function signature.
template<A>
void func(A bla) {
// Function logic using type A
}
### 7.2 Class Templates
Classes can also be templated. Template parameters propagate to the class scope and can be used for inheritance or member definitions.
template<N>
class try1 : public N {
public:
N value;
};
### 7.3 Templated Class Method Definitions
When defining methods for a templated class outside the class body, the class-level template parameters automatically propagate into the function scope. Because the template parameters are defined at the class level, they are already in scope. Therefore, the class name in the out-of-line definition does not need to explicitly repeat the template arguments (e.g., `try1::func` is valid and preferred over `try1<N>::func`). The explicit `this` pointer retains the class type.
[CODE]
template<K, V>
class Dictionary {
public:
K key;
V value;
};
// The template parameters 'K' and 'V' from the class are automatically available here.
// No need to write Dictionary<K, V>::setValue
public void Dictionary::setValue(Dictionary* this, K k, V v) {
this->key = k;
this->value = v;
}
[/CODE]
### 7.4 Additional Method-Level Template Parameters
You can introduce new template parameters specifically for a class method, in addition to the class-level template parameters.
[CODE]
template<B>
public void Dictionary::processAndStore(Dictionary* this, K k, V v, B metadata) {
// Logic using class templates 'K', 'V' and method template 'B'
this->key = k;
this->value = v;
print("Metadata type: ${typeof(metadata)}");
}
[/CODE]
### 7.5 Template Instantiation Syntax
Templates must be instantiated with concrete types before the compiler can generate the final code. SL supports both explicit instantiation and automatic type inference.
#### 7.5.1 Function Template Instantiation
For function templates, you can either explicitly specify the template arguments using angle brackets `< >`, or rely on the compiler to infer the types from the function arguments.
[CODE]
template<T>
void printValue(T val) {
// Logic to print val
}
int32 main() {
// 1. Explicit Instantiation: The developer specifies the type.
printValue<int32>(42);
printValue<float32>(3.14);
// 2. Type Inference: The compiler deduces 'T' from the argument type.
printValue(100);    // Compiler infers T = int32
printValue(2.71);   // Compiler infers T = float64
return 0;
}
[/CODE]
#### 7.5.2 Class Template Instantiation
Class templates always require explicit instantiation. The compiler cannot infer class template parameters from a declaration alone. Angle brackets `< >` are used immediately following the class name.
[CODE]
template<N>
class try1 {
public:
N value;
};
int32 main() {
// Explicit instantiation of a class template
try1<int32> t1;
t1.value = 42;
try1<float32> t2;
t2.value = 3.14;
// Pointers to templated classes also require explicit types
try1<int32>* ptr = new try1<int32>();
delete ptr;
return 0;
}
[/CODE]
#### 7.5.3 Mixed Inference and Explicit Parameters
If a function template has multiple parameters, you can explicitly specify some and let the compiler infer the rest. Explicit parameters are resolved from left to right.
[CODE]
template<A, B>
void process(A id, B data) {
// Logic using A and B
}
int32 main() {
// Explicitly specify 'A' as int32, let compiler infer 'B' as float32
process<int32>(10, 3.14);
// Explicitly specify both 'A' and 'B'
process<int32, float32>(10, 3.14);
return 0;
}
[/CODE]
## 8. TYPEDEF
The `typedef` keyword is used to create an alias for an existing type.
This improves code readability and maintainability without creating a new distinct type.
### 8.1 Syntax
typedef <existing_type> <new_type_name>;
### 8.2 Examples
// Alias for a primitive type
typedef int32 Score;
typedef uint64 MemoryAddress;
// Alias for a pointer type
typedef char* String;
// Alias for a class type
typedef try1<int32> IntTry1;
### 8.3 Usage Rules
- Typedefs can be used anywhere a primitive or class type is expected.
- Typedefs do not create strong typing; a `Score` is still fully compatible with an `int32`.
- Typedefs can be declared at the global scope or within a specific scope (e.g., inside a function or class).
- Typedefs can be exported (e.g., `export typedef int32 Score;`), making the alias visible to importing modules alongside the underlying type's visibility rules.
## 9. CONTROL FLOW
SL supports standard control flow structures:
- Conditional: `if`, `else`
- Loops: `while`, `do-while`, `for`
- Branching: `switch`, `case`, `default`, and modern `match`
- Jump Statements: `break`, `continue`, `return`
### 9.1 Pattern Matching (`match`)
The match expression is a modern, safe alternative to traditional C-style switch statements. It is designed primarily for enum and tagged union types, and can also match on integer values and type hashes (see 9.1.5).
Unlike `switch`, `match` is an **expression** (it evaluates to a value), **never falls through**, and enforces **exhaustiveness checking** at compile time. Commas between match arms are not required, and trailing commas after the last match arm are optional and allowed. The `{}` block boundary is sufficient.
#### 9.1.1 Basic Syntax and Expression Usage
Because `match` evaluates to a value, it can be directly assigned to a variable or returned from a function.
[CODE]
enum class Status : int32 {
	OK = 0,
	ERROR = 1,
	PENDING = 2
};
int32 handleStatus(Status s) {
	// 'match' evaluates to an int32, so we can return it directly.
	// The compiler enforces that all variants are covered.
	return match (s) {
		Status::OK => 0,
		Status::ERROR => -1,
		Status::PENDING => 1
	};
}
[/CODE]
#### 9.1.2 Statement Usage and Wildcards
If you only need to execute code blocks without returning a value, you can use block syntax. The `_` symbol acts as a catch-all wildcard (similar to `default` in a `switch`), which is required if not all enum variants are explicitly listed.
[CODE]
match (s) {
	Status::OK => {
		print("Success");
	}
	Status::ERROR => {
		print("Failed");
	}
	_ => {
		// Wildcard handles PENDING or any future variants added to the enum
		print("Unknown state");
	}
}
[/CODE]
#### 9.1.3 Tagged Union Destructuring (Sum Types)
Raw C-style `union` types (Section 14.4) do not track which member is active, making them unsafe for pattern matching. To solve this, SL introduces **Tagged Unions** (Sum Types) using parameterized `enum class` declarations.
A parameterized `enum class` compiles down to a highly efficient, packed C-struct containing an integer tag and a raw union. The `match` statement can safely destructure these types, automatically binding the inner data to local variables based on the active tag.
[CODE]
// 1. Defining a Tagged Union
enum class Result : int32 {
	Success(int32 code),
	Error(char* msg)
};
// 2. Safe Destructuring via `match`
void processResult(Result res) {
	match (res) {
		// 'code' is automatically bound and available as int32
		Result::Success(code) => {
			print("Code: ${code}");
		}
		// 'msg' is automatically bound and available as char*
		Result::Error(msg) => {
			print("Error: ${msg}");
		}
	}
}
// 3. Wildcards and Ignoring Data
// Use '_' to ignore the bound data if you only care about the variant
match (res) {
	Result::Success(_) => print("Operation succeeded")
	_ => print("Operation failed")
}
[/CODE]
#### 9.1.4 Key Advantages over `switch`
1. **No Fall-through**: Each branch is strictly isolated. Forgetting a `break` is impossible.
2. **Exhaustiveness Checking**: The compiler guarantees all possible states are handled, preventing silent logical bugs when new enum variants are added.
3. **Zero Runtime Cost**: `match` compiles down to the exact same highly optimized asm.js `switch` statement or jump table as a traditional C `switch`. The safety guarantees are 100% compile-time.
#### 9.1.5 Matching Non-Enum Values (Integers and Type Hashes)
match may also be used on integer scrutinees, including uint64 type hash values.
Exhaustiveness rule:
- Closed sets (enum, enum class, tagged unions): the compiler enforces that every variant is covered, or that a _ wildcard is present.
- Open sets (any integer type, type hashes, generic template parameters): the _ wildcard is MANDATORY, because the compiler cannot enumerate every possible value.
This is the same rule already used by match type with generic parameters (9.2.2).
Patterns on integer scrutinees must be compile-time constants. Compile-time intrinsics such as hashtype(Type) and __builtin_type_id(Type) are officially supported constant patterns.
[CODE]
match (__builtin_va_current_type(ap)) {
	hashtype(int32)   => print("int32")
	hashtype(float32) => print("float32")
	_ => print("unknown")
}
[/CODE]
### 9.2 Compile-Time Type Matching (`match type`)
While standard match evaluates runtime values, match type evaluates the static compile-time type of an expression. It matches by type hash (the same hashtype mechanism as 3.7), so it is the same type-identity system as typeof, not a separate one. It carries no runtime overhead and requires no RTTI.
#### 9.2.1 Syntax and Smart Casting
The `match type` construct compares the static type of an expression against a list of types. Inside a matched branch, the expression is **smart-cast** (narrowed) to the matched type, allowing direct access to type-specific members without explicit casting.
[CODE]
template<T>
void analyze(T data) {
	match type (data) {
		int32 => {
			// 'data' is treated as int32 here.
			print(data + 10);
		}
		float32 => {
			// 'data' is treated as float32 here.
			print(data * 1.5);
		}
		MyClass* => {
			// 'data' is treated as MyClass* here.
			data->update();
		}
		_ => {
			// Wildcard handles any other type.
			print("Unknown type");
		}
	}
}
[/CODE]
#### 9.2.2 Exhaustiveness and Zero-Cost Guarantee
- **Zero Runtime Cost:** The compiler resolves `match type` entirely during compilation. The generated asm.js contains **only** the code for the matching branch. All other branches are dead-code eliminated.
- **Exhaustiveness:** If the expression's type is fully resolved (e.g., a concrete variable), the compiler enforces that all possibilities are covered or a `_` wildcard is provided. If the expression is a generic template parameter (e.g., `T`), a `_` wildcard is **mandatory** because the compiler cannot guarantee all possible instantiations are covered.
- Matching is performed on hashtype values. A hash of 0 (unknown type) never matches a named type branch and falls through to the _ wildcard.
## 10. DEFERRED RESOLUTION AND ORDERING
The SL compiler employs a multi-pass deferred resolution strategy. This means the order of declarations and definitions in the source file does not strictly matter, as long as all symbols are eventually defined within the compilation unit. This allows for flexible code organization without the strict need for forward declarations.
// Function using 'try1' before it is defined
void out(try1 t) {
// Compiler defers type resolution
}
// Class defined later in the file
class try1 {
public:
int32 x;
};
Note: While deferred resolution handles most cases, explicit forward declarations (e.g., `class try1;`) are still supported and recommended for resolving complex circular dependencies or when returning pointers/references to incomplete types.
## 11. SUMMARY OF KEY DESIGN CHOICES
1. Explicit `this`: Promotes clarity, prevents hidden magic, and makes SL highly compatible with C-style ABIs.
2. No Inline Class Methods: Keeps class definitions clean, acting strictly as data schemas (similar to C structs or Rust's trait/implementation separation).
3. Predictable Layout On Request: Layout is natural and optimized by default. Adding __attribute__((packed)) gives a padding-free, predictable layout, ideal for systems programming, networking, serialization, and file I/O.
4. Static Lifecycle Hooks: Provides built-in, deterministic startup and shutdown logic per class/module without requiring manual registration.
5. Flexible Export Naming: Allows precise control over symbol names in compiled binaries for seamless FFI (Foreign Function Interface) and dynamic linking.
6. Explicit Templating: Provides powerful generic programming capabilities while maintaining clear separation between class-level and method-level type parameters.
7. Deferred Resolution: Eliminates rigid top-down ordering requirements, allowing functions and classes to reference each other freely as long as they are defined within the compilation unit.
## 12. EXECUTION MODEL AND ENTRY POINT
Every SL executable must define a global entry point function named `main`. The runtime environment handles static initialization (static constructors) before transferring control to `main`.
### 12.1 The `main` Function
The `main` function can be defined with or without command-line arguments. It must return an `int32` representing the exit code to the operating system (0 for success).
// Standard entry point without arguments
int32 main() {
	return 0;
}
// Entry point with command-line arguments
int32 main(int32 argc, char** argv) {
	// argc: argument count
	// argv: array of string pointers (null-terminated)
	return 0;
}
### 12.2 Execution Lifecycle
1. OS loads the binary.
2. SL Runtime initializes.
3. All `static` class constructors (Section 5.4) are executed in dependency order.
4. `main()` is called.
5. Upon `main()` returning, all `static` class destructors are executed in reverse order.
6. Process terminates with the return value of `main()`.
## 13. MEMORY MANAGEMENT
SL provides both low-level C-style memory management and high-level object-oriented allocation keywords. Under the hood, `new` and `delete` are syntactic sugar that utilize `malloc`, `realloc`, and `free` via the C standard library (compiled to asm.js using a SharedArrayBuffer).
### 13.1 Allocation and Deallocation
- `malloc(uint64 size)`: Allocates a raw block of memory of the specified size in bytes.
- `realloc(void* ptr, uint64 size)`: Resizes a previously allocated memory block.
- `free(void* ptr)`: Deallocates a raw memory block.
- `new`: Allocates memory for a single object on the heap, automatically calculating the size, and calls its constructor.
- `delete`: Deallocates memory for a single object. The compiler handles the necessary size calculations and calls the object's destructor.
- `new[]`: Allocates memory for an array of objects on the heap. The compiler stores hidden metadata (such as element count) to correctly invoke the constructor for each element.
- `delete[]`: Deallocates memory for an array of objects. The compiler reads the hidden metadata to correctly invoke the destructor for every element in the array before freeing the memory block.
[CODE]
MyClass* obj = new MyClass();
delete obj;
int32* arr = new int32[100];
delete[] arr;
MyClass* objArr = new MyClass[50]; // Calls constructor 50 times
delete[] objArr; // Calls destructor 50 times, then frees memory
[/CODE]
Note: Unlike single object allocation, array allocation requires the compiler to manage allocation metadata to correctly invoke constructors during `new[]` and destructors during `delete[]`. Failing to use `delete[]` for an array allocated with `new[]` results in undefined behavior, as destructors will not be called and memory corruption may occur.
### 13.2 The Null Pointer Literal
The keyword `null` represents a null pointer (an address of zero). It can be assigned to any pointer type. Dereferencing `null` results in undefined behavior (typically a segmentation fault).
int32* ptr = null;
if (ptr != null) {
// safe to use
}
## 14. ADVANCED TYPE SYSTEM
### 14.1 Reference Types (`&`)
References provide an alias to an existing variable. Unlike pointers, references cannot be null, cannot be reseated (reassigned to point to a different variable), and do not require explicit dereferencing.
int32 x = 10;
int32& ref = x; // ref is an alias for x
ref = 20;       // x is now 20
// References are heavily used in function parameters to avoid pointer syntax
void modifyValue(int32& val) {
val = 100;
}
### 14.2 Array Types
Fixed-size arrays are declared using square brackets. Arrays are value types but decay to pointers when passed to functions expecting a pointer, ensuring C-ABI compatibility.
Note: SL fixed-size arrays do NOT have a `.length` property or automatic runtime bounds checking. The size must be tracked manually or passed alongside the pointer when decayed.
int32 numbers[5] = {1, 2, 3, 4, 5};
char buffer[256];
// Array decay
void process(int32* data, int32 length) { ... }
process(numbers, 5); // 'numbers' decays to int32*
### 14.3 Enumerations (`enum` and `enum class`)
Enumerations define a set of named integer constants. By default, they start at 0 and increment by 1. The underlying type defaults to `int32` but can be specified.
// Unscoped enumeration (values leak into the enclosing scope)
enum Color {
RED,
GREEN,
BLUE
};
enum Status : uint8 {
OK = 0,
ERROR = 1,
PENDING = 2
};
Color c = GREEN;
// Scoped enumeration (`enum class`)
// Values are strictly scoped to the enum name and do not implicitly convert to integers, providing stronger type safety.
enum class Direction : int8 {
UP = 1,
DOWN = -1
};
Direction d = Direction::UP;
// int32 val = d; // Error: requires explicit cast
int32 val = (int32)d; // Valid explicit cast
// Memory Ordering Enumerations (for atomic operations, see Section 24)
enum class MemoryOrder : int8 {
RELAXED = 0,
CONSUME = 1,
ACQUIRE = 2,
RELEASE = 3,
ACQ_REL = 4,
SEQ_CST = 5
};
### 14.3.1 Tagged Unions (Parameterized Enum Classes)
By adding data payloads to an enum class, you create a Tagged Union (Sum Type). The compiler generates a struct containing the underlying integer tag and a raw union of the payload types. Like all classes and structs in SL, this layout follows natural alignment and padding by default. If a padding-free layout is required, the enum class can be explicitly marked with __attribute__((packed)), aligning with the rules in Section 5.2.1.
[CODE]
enum class Shape : int8 {
Circle(float32 radius),
Rectangle(float32 width, float32 height)
};
// Underlying Memory Layout (Packed):
// struct Shape {
//     int8 tag;
//     union {
//         float32 Circle_radius;
//         struct { float32 Rectangle_width; float32 Rectangle_height; } Rectangle_data;
//     } data;
// };
Shape s = Shape::Circle(5.0);
[/CODE]
### 14.4 Union Types
Unions allow storing different data types in the same memory location. The size of a union is the size of its largest member (plus any alignment padding unless the union is declared __attribute__((packed))).
[CODE]
union Data {
int32 i;
float32 f;
char c;
};
Data d;
d.i = 42;
// d.f now holds the float representation of the bits in d.i
[/CODE]
### 14.5 Tuple Returns via Reference Displacement
To maintain strict C-ABI compatibility, guarantee predictable memory layouts, and optimize for WebAssembly (which natively handles multi-value returns via pointers), SL implements tuple returns as **syntactic sugar for out-parameters**.
Instead of returning a copied struct, the compiler displaces the tuple elements to the front of the function's argument list as references (pointers). No hidden struct copying occurs; the function writes directly to the caller's memory.
#### 14.5.1 Named Tuple Returns (Recommended)
For the best readability, you can name the return variables directly in the signature. The compiler displaces them to the front as out-parameters, but inside the function body, they act as pre-declared aliases to those out-parameters.
// Definition with named returns.
// The compiler transforms this into: void calculate(int32* out_code, float32* out_value)
(int32 code, float32 value) calculate() {
// You can assign to the named returns directly throughout the function.
code = 200;
value = 3.14;
// A bare 'return;' exits the function, returning the current values.
return;
}
// You can also use the `return (val1, val2)` syntax candy:
(int32 code, float32 value) calculateAlt() {
// Equivalent to: code = 200; value = 3.14; return;
return (200, 3.14);
}
// Call Site: Destructuring into existing variables.
// The compiler translates this to: calculate(&c, &v)
int32 c;
float32 v;
(c, v) = calculate();
print(c); // Prints 200
print(v); // Prints 3.14
// Or declare and destructure in one step:
(int32 c2, float32 v2) = calculate();
#### 14.5.2 Anonymous Tuple Returns
You can also define a tuple return using references without naming them. The caller still provides the memory.
// Definition: The compiler transforms this into void getValues(int32* out0, float32* out1)
(int32&, float32&) getValues() {
return (123, 3.14);
}
// Call Site: The compiler translates this to getValues(&x, &y)
int32 x;
float32 y;
(x, y) = getValues();
#### 14.5.3 Mixing with Standard Parameters
Reference tuple returns are always displaced to the *front* of the parameter list to maintain a consistent ABI.
(int32 x, float32 y) compute(int32 multiplier, float32 offset) {
x = 10 * multiplier;
y = 2.5 + offset;
return;
}
int32 a;
float32 b;
(a, b) = compute(5, 1.0); // Compiles to: compute(&a, &b, 5, 1.0)
#### 14.5.4 Class Implementations and Exports
When defining a class function with tuples, this is how the class function is defined.
(int32& x, float32& y) classname::func(classname* this, int32 param)
On export, the out-parameters are always placed after `this` to preserve C-style naming and ABI conventions. Both pointer (int32* x) and reference (int32& x) syntax are supported in the SL source code, as the compiler lowers both to pointer out-parameters in the generated C-ABI.
void classname::func(classname* this, int32* x, float32* y, int32 param);
For throwable functions the order is: this (if a method), then error pair, then the tuple return out-parameters, then the regular parameters.
#### 14.5.5 Implementation Details
- **No hidden struct copying occurs.** The function writes directly to the caller's memory.
- **asm.js ABI:** This maps 1:1 to asm.js pointer-based multi-value return conventions. In the generated asm.js, the function signature uses SharedArrayBuffer indices to emulate pointer out-parameters.
- **Named Aliases:** When named returns are used, the compiler maps the local variable names (`code`, `value`) directly to the out-parameter pointers in the asm.js environment.
- **Bare Return:** A bare `return;` in a tuple-returning function simply generates a standard void return in asm.js, since the values have already been written to the out-parameters.
- asm.js: the error pair becomes two additional pointer parameters (SharedArrayBuffer indices) ahead of the tuple out-parameters. The function still returns void.
## 15. MODULES, IMPORTS, AND INTEROPERABILITY
### 15.1 Importing Modules
To use definitions from other SL files, SL provides two directives that serve different purposes:
- #import "file.sl": Includes ONLY the exported symbols from the specified file. Private/protected members and non-exported symbols remain hidden. This is the recommended way to manage the global namespace.
- #include "file.sl": Performs a full textual inclusion of the file, making ALL symbols (exported and non-exported) available in the current compilation unit. Use this with caution to avoid namespace pollution.
#import "math_utils.sl"
#import "networking.sl"
### 15.2 C Interoperability (`extern`)
To call functions from external C libraries or expose SL functions to C, use the `extern "C"` block. This disables SL's name mangling and enforces the C calling convention.
extern "C" {
// Importing a C standard library function
void* malloc(uint64 size);
void free(void* ptr);
// Exporting an SL function to C
export int32 sl_calculate(int32 a, int32 b);
}
## 16. FUNCTIONS, SCOPE, AND NAMESPACES
### 16.1 Namespaces
Namespaces provide a way to group related symbols and prevent name collisions. The `::` operator is used to access namespace members.
namespace Math {
int32 add(int32 a, int32 b) { return a + b; }
namespace Trigonometry {
float32 sin(float32 angle);
}
}
int32 result = Math::add(5, 10);
float32 val = Math::Trigonometry::sin(3.14);
### 16.2 Function Overloading
SL supports function overloading. Multiple functions can share the same name as long as their parameter lists (types, counts, or const-qualifiers) differ. The compiler resolves the correct function at compile time.
void print(int32 val);
void print(float32 val);
void print(const char* val);
print(42);    // Calls print(int32)
print(3.14);  // Calls print(float32)
### 16.3 Default Parameters and Variadic Functions
Functions can specify default values for trailing parameters. Variadic functions accept a variable number of arguments using `...`.
void drawRect(int32 x, int32 y, int32 width = 10, int32 height = 10);
drawRect(5, 5);        // width=10, height=10
drawRect(5, 5, 20);    // width=20, height=10
// Variadic function (similar to C's printf)
void log(const char* format, ...);
### 16.4 Anonymous Functions (Lambdas)
SL supports anonymous functions (lambdas) for inline logic and callbacks. Lambdas can be directly assigned to function pointers. To maintain clean syntax while guaranteeing memory safety and C-ABI compatibility, the compiler automatically generates a hidden thunk to bridge any captured closure state to the function pointer call.
// 1. Basic Syntax and Function Pointer Assignment
void(*fptr)() = void()->{};
int32(*fptr2)(int32) = int32(int32 n)->{ return n + 1; };
(int32&, float32&)(*fptr3)() = (int32& x, float32& y)->{ x = 123; y = 1.23; };
// 2. Tuple Return Lambdas
// Lambdas can also return tuples, matching the tuple return syntax of regular functions.
(int32 x, float32 y) fptr4();
// 3. Automatic Safe Capturing (Hidden refclass)
// If a lambda accesses an outer local variable, the compiler automatically
// wraps the captured state in a hidden 'refclass' behind the scenes.
// Primitive types (like int32) are copied by value into this hidden closure.
// The closure object itself is reference-counted, ensuring the captured
// state remains alive as long as the function pointer exists, preventing
// dangling stack pointers without requiring explicit capture lists.
int32 multiplier = 5;
int32(*multiply)(int32) = int32(int32 x)->{
	return x * multiplier; // 'multiplier' is safely copied by value into the hidden closure
};
// 4. Variable Shadowing
// Declaring a variable with the same name inside the lambda shadows the outer variable.
int32 x = 123;
void(*shadowTest)() = void()->{
	int32 x = 0; // This is a local 'x', it does not affect the outer 'x'
	print(x);    // Prints 0
};
// 5. Passing Lambdas to Functions
// Use 'typedef' to define clean function signatures for accepting lambdas.
typedef int32(int32, int32) MathOperation;
public void calculate(MathOperation* op, int32 a, int32 b) {
	int32 result = op(a, b); // Invoke the passed lambda via the hidden thunk
	print(result);
}
int32 main() {
	int32(*myOp)(int32, int32) = int32(int32 a, int32 b)->{ return a * b; };
	calculate(&myOp, 5, 4); // Pass address of the function pointer
	return 0;
}
## 17. OBJECT-ORIENTED REFINEMENTS
### 17.1 `struct` vs `class`
Both `struct` and `class` define data layouts. The only difference is default visibility:
- `class`: Members default to `private`.
- `struct`: Members default to `public`.
Otherwise, they are identical (both support inheritance, no inline methods, explicit `this`).
### 17.2 Virtual Methods and Explicit Abstract Classes
To enable dynamic dispatch (polymorphism) and explicitly mark a class as abstract, use the `virtual` keyword. A class with at least one unimplemented `virtual` method is strictly abstract and cannot be instantiated.
class Shape {
	public:
	int32 x, y;
};
// Explicitly virtual. If not implemented in a derived class, Shape is abstract.
public virtual void Shape::draw(Shape* this);
class Circle : public Shape {
};
// Implementation makes Circle concrete
public void Circle::draw(Circle* this) {
	// draw circle logic
}
Shape* s = new Circle();
s->draw(); // Calls Circle::draw via dynamic dispatch
Object layout: A class that declares at least one virtual method (or inherits one) receives an explicit, accessible integer field named `_systemVtableIndex`. This field is not hidden; it is directly readable and writable by the developer (e.g., `classobj._systemVtableIndex`). It is placed and aligned like any other field (or packed, if the class is declared `__attribute__((packed))`) and counts toward `sizeof`.
Crucially, SL uses this vtable INDEX, never a raw vtable pointer (vptr). Because the object carries an accessible integer index instead of a memory address, objects with virtual methods are fully serializable for transportation and deserializable by the developer. This ensures objects remain valid and safe to pass across network boundaries and WebAssembly shared memory worker boundaries without pointer invalidation. At runtime, the compiler-generated code uses this index to look up the correct function pointer in a globally unique, module-level vtable array associated with the class hierarchy.
### 17.3 Member Initialization
Class members can be initialized directly in the class definition. These default values are applied before the constructor body executes.
class Config {
	public:
	int32 timeout = 30;
	bool isEnabled = true;
	const char* name = "default";
};
## 18. EXPRESSIONS, LITERALS, AND CASTING
### 18.1 Literal Formats
- Integers: Decimal (`123`), Hexadecimal (`0xFF`), Octal (`077`), Binary (`0b1010`). Suffix `U` for unsigned (e.g., `123U`), `LL` for 64-bit (e.g., `123LL`).
- Floats: Decimal (`3.14`), Scientific (`1.5e-3`). Suffix `f` for 32-bit float (e.g., `3.14f`), otherwise defaults to 64-bit `float64`.
- Booleans: `true` and `false`.
### 18.2 Type Casting
SL supports both implicit safe casting and explicit unsafe casting.
- Implicit: Smaller to larger types (e.g., `int8` to `int32`), non-pointer to `void*`.
- Explicit C-style: `(Type)expression`. Used for narrowing conversions or pointer casting.
- Explicit Safe Cast: `cast<Type>(expression)`. Performs runtime checks if applicable (e.g., downcasting polymorphic pointers). The compiler validates the dynamic type by comparing the object's hidden vtable index (as described in Section 17.2) against the target type's compile-time index, ensuring type safety without raw pointer dereferencing.
int32 i = 100;
int8 small = (int8)i; // Explicit narrowing
void* ptr = null;
int32* intPtr = (int32*)ptr; // Explicit pointer cast
Shape* base = new Circle();
Circle* derived = cast<Circle*>(base); // Safe downcast
## 19. ERROR HANDLING AND DIAGNOSTICS
### 19.1 Assertions
The `assert` keyword evaluates a boolean expression. If false, it halts execution and prints diagnostic information (file, line, expression). Used for catching logical errors during development.
assert(ptr != null);
assert(index >= 0 && index < length);
### 19.2 Exceptions (`try`, `catch`, `throw`, `throwable`)
For recoverable runtime errors, SL provides a lightweight, zero-overhead exception mechanism based on explicit error propagation. Unlike traditional stack-unwinding exceptions, SL uses tuple-based error returns under the hood, ensuring C-ABI compatibility and predictable performance.
#### 19.2.1 The `throwable` Keyword
Any function or class method that can throw an exception must explicitly declare the `throwable` keyword in its signature.
If a function calls a `throwable` function, it must either:
1. Encapsulate the call within a `try-catch` block.
2. Declare itself as `throwable`, allowing the error to bubble up the call stack.
If a non-`throwable` function calls a `throwable` function without encapsulating it in a `try-catch` block, the compiler will emit a compile error.
// A function that can throw an error
void openFile(const char* path) throwable {
	if (!fileExists(path)) {
		throw new Error("File not found");
	}
}
#### 19.2.2 Developer Syntax: `try`, `catch`, and `throw`
Developers use standard `try` and `catch` blocks to handle exceptions. The `catch` block specifies the expected error type (e.g., a pointer to an `Error` class). The variable declared in the `catch` condition is strictly scoped to the `catch` block body.
try {
	openFile("data.txt");
} catch (Error* err) {
	print("Failed to open file: ");
	print(err->getMessage());
} catch (...) {
	// Catch-all block for any other exception type
	print("Unknown error occurred");
}
To partially handle an error and bubble it up to the next level, use a standalone `throw;` statement inside the `catch` block. This re-throws the exact same error object to the next enclosing scope without allocating new memory.
#### 19.2.3 Compiler Implementation (Under the Hood)
A throwable function is always lowered as a tuple-returning function, using the same out-parameter displacement rule as Section 14.5. The error pair (void** err_ptr, uint64** type_id) is placed FIRST, ahead of the function's own return values and parameters. The compiler wires the error information into those slots; this is the same mechanism as 14.5, not a separate code path.
1. Void: void func() throwable
becomes void func(void** err_ptr, uint64** type_id)
2. Value return: int32 func() throwable
becomes void func(void** err_ptr, uint64** type_id, int32* ___ret)
3. Class method: void classname::func(classname* this) throwable
becomes void classname::func(classname* this, void** err_ptr, uint64** type_id)
4. Tuple return: (int32 code, float32 value) calculate() throwable
becomes void calculate(void** err_ptr, uint64** type_id, int32* code, float32* value)
5. Combined (Class Method + Tuple Return + Throwable):
(int32 code, float32 value) MyClass::compute(MyClass* this, int32 param) throwable
becomes void MyClass::compute(MyClass* this, void** err_ptr, uint64** type_id, int32* out_code, float32* out_value, int32 param)
#### 19.2.4 Execution Flow and Error Propagation
- On `throw`: Inside a `throwable` function, executing a `throw` statement populates the internal error structure with the object's pointer and its compile-time type ID, then returns immediately. No stack unwinding is necessary. However, all `defer` statements in the current scope are guaranteed to execute in reverse order before the function actually returns.
- On Success: If the function completes normally without throwing, the hidden error pointer is automatically set to `0` (`null`) and `type_id` to `0` before returning.
- Caller Check: The calling (upper) function receives the tuple. The compiler automatically inserts a check: if the error pointer is non-zero, it compares the `type_id` against the available `catch` blocks. If a match is found, it performs a small, direct jump to that `catch` block. If the error pointer is `0`, it executes as normal.
#### 19.2.5 Error Memory Lifecycle
When an exception is thrown using `throw new Error(...)`, memory is allocated on the heap for the error object. This object is passed up the call stack via the hidden error pointer.
Crucially, the error object is automatically deleted and freed from memory immediately after the `catch` block finishes executing. The compiler automatically injects the necessary cleanup code (equivalent to `delete err;`) at the end of the catch scope.
- Re-throw Logic: If a `catch` block executes a standalone `throw;` to re-propagate the error, the compiler recognizes the error pointer is unchanged and skips deletion. If the `catch` block throws a *new* error (e.g., `throw new Error("...");`), the compiler automatically deletes the original error pointer before propagating the new one, preventing memory leaks.
- Catch-All Cleanup: When using `catch (...)`, the compiler does not have a named variable to delete. To prevent memory leaks, the compiler automatically injects a call to a universal runtime deallocator to free the heap-allocated object safely based on the internal type ID.
- Note on `refclass` Exceptions: If a `refclass` instance is thrown, the `throw` keyword temporarily increments its reference count. The compiler automatically injects a `release()` call when the `catch` block exits, ensuring no memory leaks.
Note on Constructors and Destructors: Graceful backtracking during object construction is the responsibility of the developer. If a constructor throws, the compiler has already allocated the object's memory, but it does not automatically unwind or destroy partially initialized members. Developers should use `defer` or explicit cleanup within the constructor to handle partial allocation failures safely.
This design guarantees that exception handling has zero runtime overhead when no errors occur, and provides deterministic, explicit error propagation and cleanup that maps perfectly to WebAssembly and asm.js targets.
## 20. COMPILER DIRECTIVES AND QUALIFIERS
### 20.1 `volatile` Qualifier
The `volatile` keyword tells the compiler not to optimize accesses to a variable, ensuring every read/write goes directly to memory. Essential for memory-mapped hardware registers and signal handlers.
volatile int32* hardwareRegister = (int32*)0x40021000;
*hardwareRegister = 0xFF; // Guaranteed to write to memory
### 20.2 `inline` Hint
The `inline` keyword suggests to the compiler that a function's body should be inserted at the call site to reduce function call overhead. (Note: This does not apply to class methods, which are never inline per Section 5.1).
inline int32 square(int32 x) {
	return x * x;
}
### 20.3 Operator Precedence
SL follows standard C/C++ operator precedence. For example, `*` and `/` bind tighter than `+` and `-`. Parentheses `()` should be used to clarify complex expressions.
### 20.4 `defer` Statement
SL supports the `defer` statement (similar to Go or Zig). A `defer` block schedules an expression or statement to be executed when the current scope exits. The "scope" is strictly defined as the immediate enclosing `{}` block. This is invaluable for localized cleanup (e.g., `defer free(ptr);`) without needing wrapper classes or complex try/finally blocks.
[CODE]
if (condition) {
	void* ptr = malloc(100);
	defer free(ptr); // Executes exactly when this 'if' block ends
	// ...
}
[/CODE]
### 20.5 Reference Counted Classes (`refclass`)
A `refclass` is like a `class`, but behind the scenes, the compiler implements a full reference-counting mechanism.
- The constructor initializes the reference count to 1.
- When a `refclass` instance is assigned or copied, the count is incremented.
- The `=` operator checks if the argument is the same instance (via pointer comparison) to avoid self-assignment issues.
- The destructor decrements the count and frees the memory automatically when the count reaches zero.
Note on Memory Layout: Like classes with virtual methods (Section 17.2), the hidden reference count field is managed by the compiler and counts toward the class's `sizeof` and alignment requirements.
refclass classname {
// Same syntax and rules as a standard class
};
Class functions are declared the same way as standard classes. `export refclass` and `refclass` inheritance follow the same rules as standard classes.
### 20.6 Type Inference (`auto`)
The `auto` keyword is supported for local variable type inference, allowing the compiler to deduce the type directly from the initializer expression.
auto x = 123; // Compiler deduces 'int32'
## 21. PREPROCESSOR MACROS AND CONDITIONAL COMPILATION
Preprocessor macros in SL are handled by the Small Language Preprocessor (SLP) interpreter.
Refer to `SLPDoc.txt` for complete SLP documentation.
Preprocessor logic blocks are enclosed between `#<` and `>#`. Within these blocks, you can define `#token` variables that drive both macro substitution and conditional compilation.
### 21.1 Defining Tokens
#<
#token var DEBUG_MODE = true;
#token var TARGET_WASM = 1;
#>
### 21.2 Conditional Compilation Directives
SL supports standard conditional compilation directives that evaluate the existence and truthiness of SLP `#token`s. This is highly useful for targeting different environments (e.g., Native asm.js vs. WebAssembly) or toggling debug features without runtime overhead.
Supported Directives:
- `#ifdef TOKEN_NAME` : Includes the block if the token is defined and evaluates to true.
- `#ifndef TOKEN_NAME`: Includes the block if the token is NOT defined or evaluates to false.
- `#else`             : Fallback block if the preceding `#ifdef`/`#ifndef` condition fails.
- `#elif TOKEN_NAME`  : Else-if condition, checked sequentially.
- `#endif`            : Terminates the conditional block.
Example Usage:
#<
#token var TARGET_WASM = true;
#token var WASM_SHARED_MEMORY = true;
#>
#ifdef TARGET_WASM
// This code is ONLY compiled when TARGET_WASM is true
extern "C" {
export void wasm_specific_init();
}
#else
// This code is compiled for native targets
void native_specific_init();
#endif
#ifdef WASM_SHARED_MEMORY
// Backend allocates shared linear memory; atomics compile to WASM atomic instructions
#else
// Backend allocates standard linear memory; atomics downgrade to standard loads/stores
// with a compiler warning, or fail to compile if strict thread-safety is enforced.
#endif
int32 main() {
#ifdef DEBUG_MODE
print("Running in debug mode");
#endif
return 0;
}
### 21.3 Preprocessor Execution Order and Block Syntax
All SLP logic, including token definitions and conditional directives, can be placed anywhere in the SL source file. Blocks containing SLP script logic must be enclosed in the `#<` and `>#` delimiters. Standalone `#ifdef`/`#endif` directives outside of `#< >#` blocks are also valid and will reference tokens defined globally or in previously evaluated SLP blocks.
#### 21.3.1 Compilation Passes and Execution Timing
The execution of the SLP engine relative to the main SL compiler depends on the specific implementation, but generally follows these rules:
1. First-Pass Execution (Standard):
The SLP engine strictly runs as a first pass. All `#token` definitions must appear textually before they are used in `#ifdef` directives or evaluated. The preprocessor functions are declared and able to be used on the first pass, and the preprocessor can be called to get the values during this pass.
Regardless of the pass, the SLP engine guarantees that all preprocessor logic is fully resolved and expanded before the final code generation (asm.js) phase begins.
### 21.4 IMPLEMENTATION & COMPILER RESTRICTIONS
To ensure maximum portability and minimal overhead, the SLP implementation
adheres to strict compiler constraints:
-fno-exceptions : No C++ exceptions (throw, try, catch) are used. Errors are
handled via return types (e.g., "Parse Error: ..." or
"Runtime Error: ..." strings from define(), and "Error: ..."
strings from get()).
-fno-rtti       : No Run-Time Type Information (dynamic_cast, typeid) is used.
Type checking relies on explicit type tags (enums).
- Memory Management: Uses reference-counted std::shared_ptr<Value> objects to
prevent memory leaks during repeated define/get calls.
## 22. VARIADIC FUNCTIONS AND COMPILER INTRINSICS
To maintain strict C-ABI compatibility, guarantee predictable memory layouts, and ensure seamless WebAssembly support, SL does not use traditional C-style `va_list` macros. Instead, SL provides explicit compiler intrinsics for variadic argument handling. This approach avoids "hidden magic" and gives the compiler full control over memory management, especially for complex types like `refclass`.
### 22.1 Compiler Intrinsics
The SL compiler exposes the following built-in intrinsics for variadic operations:
- `__builtin_va_list` : An opaque type representing the argument list buffer.
- `__builtin_va_start(ap, last_param)` : Initializes the list, pointing it to the memory immediately following `last_param`.
- `__builtin_va_arg(ap, type)` : Extracts the next argument from the list, interpreting it as the specified `type`.
- `__builtin_va_current_type(ap)` : Returns the uint64 type hash (hashtype value) of the next argument in the list without advancing the pointer. Returns 0 if the type is unknown or cannot be resolved.
- `__builtin_type_id(Type)` : Compile-time intrinsic equivalent to hashtype(Type). Kept for use alongside __builtin_va_current_type.
- `__builtin_va_end(ap)` : Cleans up the list. For `refclass` objects, the compiler automatically injects memory release logic here.
### 22.2 Memory and Lifecycle Management
Under the hood, the compiler manages the variadic buffer differently based on the type being passed:
1. **Primitives and Standard `class` (Ownership Transfer)**: The compiler uses the `sizeof` operator to calculate the exact byte size. The raw bytes are copied into the variadic buffer. When extracted via `__builtin_va_arg`, this constitutes an **Ownership Transfer**: the raw bytes are read back and moved into the local variable. The compiler will only inject a destructor call at `__builtin_va_end` for class instances that were *not* extracted, preventing double-free errors.
2. **`refclass`**: Because `refclass` relies on reference counting, a raw memory copy would cause dangling pointers. When a `refclass` is pushed into the variadic list, the compiler automatically injects a `retain()` call to increment the reference count. When extracted via `__builtin_va_arg`, another `retain()` is injected for the new local variable. Finally, when `__builtin_va_end` is called, the compiler iterates through any unextracted `refclass` pointers in the buffer and injects `release()` calls to prevent memory leaks.
### 22.3 Developer Examples
#### Example 1: Handling Known Types
When the types of the variadic arguments are known in advance (e.g., a function that takes a count followed by a specific number of integers), use `__builtin_va_arg`.
[CODE]
void printNumbers(int32 count, ...) {
__builtin_va_list ap;
__builtin_va_start(ap, count);
int32 i = 0;
while (i < count) {
// Extract the next argument as an int32
int32 val = __builtin_va_arg(ap, int32);
print("Number: ${val}");
i++;
}
// Clean up the variadic list
__builtin_va_end(ap);
}
int32 main() {
printNumbers(3, 10, 20, 30);
return 0;
}
[/CODE]
#### Example 2: Traversing Unknown Types
When the function accepts a mix of unknown types, use `__builtin_va_current_type` to inspect the Type ID of the next argument before extracting it. This allows safe traversal and type-specific logic using SL's `match` expression.
[CODE]
void logMixedArgs(int32 count, ...) {
	__builtin_va_list ap;
	__builtin_va_start(ap, count);
	int32 i = 0;
	while (i < count) {
		// current_type is a type hash; 0 means unknown. Because a hash is an open set
		// of 64-bit values, the _ wildcard is required (see 9.1.5).
		uint64 current_type = __builtin_va_current_type(ap);
		match (current_type) {
			__builtin_type_id(int32) => {
				int32 val = __builtin_va_arg(ap, int32);
				print("Got integer: ${val}");
			}
			__builtin_type_id(float32) => {
				float32 val = __builtin_va_arg(ap, float32);
				print("Got float: ${val}");
			}
			__builtin_type_id(MyClass) => {
				// Extracting a standard class copies the raw bytes
				MyClass obj = __builtin_va_arg(ap, MyClass);
				print("Got MyClass instance");
			}
			__builtin_type_id(MyRefClass) => {
				// Extracting a refclass automatically increments the ref count
				MyRefClass obj = __builtin_va_arg(ap, MyRefClass);
				print("Got MyRefClass instance (ref count managed)");
			}
			_ => {
				print("Encountered unknown or unsupported type");
				// To prevent infinite loops or corruption, break or skip
				break;
			}
		}
		i++;
	}
	// __builtin_va_end automatically cleans up any unextracted refclass objects
	__builtin_va_end(ap);
}
int32 main() {
	MyClass c1;
	MyRefClass r1 = new MyRefClass();
	// Passing a mix of primitives, classes, and refclasses
	logMixedArgs(4, 42, 3.14, c1, r1);
	return 0;
}
[/CODE]
### 22.4 Implementation Notes for the Compiler Backend
- **asm.js Targets**: The intrinsics map directly to `SharedArrayBuffer` memory operations and standard JavaScript typed array manipulations. The compiler allocates a contiguous, packed memory buffer in the `SharedArrayBuffer`, writes the arguments (and their Type IDs) into this buffer, and passes the buffer's index as the `__builtin_va_list`. `__builtin_va_arg` simply reads from this linear buffer and advances the index by `sizeof(type)`.
## 23. TYPE AND FUNCTION IDENTITY HASHING
A single hashing scheme provides identity for types and functions. It is used by hashtype, typeof comparisons, match type, and the variadic intrinsics.
### 23.1 What Is Hashed
The hash is computed at compile time from a canonical string:
- Primitive types: the type name, e.g. "int32" hashes the string "int32".
- Pointer and reference types: the base name with the suffix, e.g. "int32*".
- Classes, structs, enums, unions: the FULLY-QUALIFIED name, including the whole namespace and enclosing class chain, e.g. "Math::Vector". A top-level "Vector" and Math::Vector therefore never collide.
- Functions: the fully-qualified name PLUS the parameter types (see 23.2).
### 23.2 Overloads and Parameter Mangling
Because SL supports function overloading (16.2), a function name alone is not unique. The parameter types are appended to the fully-qualified name, separated by underscores, and the result is hashed:
Math::add(int32, int32)      is hashed as  "Math::add_int32_int32"
Math::add(float32, float32)  is hashed as  "Math::add_float32_float32"
Math::Trigonometry::sin(float32) is hashed as "Math::Trigonometry::sin_float32"
Shape::draw(Shape*)          is hashed as  "Shape::draw_Shape*"
A function with no parameters hashes its fully-qualified name only. Return types are not part of the hashed name. For methods, the explicit this parameter is included like any other parameter.
### 23.3 The Zero Sentinel
A hash value of 0 is reserved to mean "unknown or unresolvable." The compiler must never produce 0 for a real type or function; if the hash algorithm yields 0, it substitutes a fixed non-zero value.
### 23.4 Guarantees
- Hashes are computed at compile time and are stable for a given name.
- Comparing hashes is a single integer comparison at runtime (or constant-folded).
- The same name always yields the same hash across compilation units, so hashes are safe to send across network or WASM worker boundaries.
### 23.5 Compiler Implementation and Customization
The compile-time type and function hashing is executed by the asm.js compiler backend. Developers building or modifying the SL compiler can integrate any hashing algorithm in the source code to suit specific performance, security, or embedding requirements. If no custom algorithm is specified, the compiler defaults to using `wyhash.hpp`, which implements the highly efficient WyHash v4 algorithm.
## 24. ATOMIC OPERATIONS AND CONCURRENCY
To support multi-threaded execution, WebAssembly shared memory, and lock-free data structures, SL provides explicit, zero-overhead atomic operations. Following SL's "no hidden magic" philosophy, atomics are handled via a type qualifier and explicit compiler intrinsics, mapping 1:1 to `SharedArrayBuffer` atomic operations in asm.js.
### 24.1 The `atomic` Type Qualifier
The `atomic` qualifier restricts atomic operations to primitive types, enums, and pointers. It guarantees that read-modify-write operations on the variable are indivisible and visible across threads according to the specified memory order.
[CODE]
atomic int32 counter = 0;
atomic bool is_ready = false;
atomic MyClass* shared_ptr = null;
[/CODE]
### 24.2 Memory Ordering
Memory ordering is controlled via the built-in `enum class MemoryOrder` (see Section 14.3). This provides strict type safety and prevents invalid integer assignments.
- `RELAXED`: No synchronization or ordering constraints, only atomicity.
- `CONSUME`: Data dependency ordering (rarely used, maps to ACQUIRE on most architectures).
- `ACQUIRE`: Ensures subsequent reads/writes are not reordered before this load.
- `RELEASE`: Ensures prior reads/writes are not reordered after this store.
- `ACQ_REL`: Combines ACQUIRE and RELEASE for read-modify-write operations.
- `SEQ_CST`: Sequentially consistent; the strongest guarantee, establishing a total order across all threads.
### 24.3 Compiler Intrinsics
Atomic operations are exposed via explicit `__atomic_` compiler intrinsics. This maintains C-ABI compatibility and avoids the need for inline class methods.
[CODE]
// Load and Store
int32 val = __atomic_load(&counter, MemoryOrder::SEQ_CST);
__atomic_store(&counter, 42, MemoryOrder::RELEASE);
// Read-Modify-Write (RMW)
int32 old_val = __atomic_fetch_add(&counter, 1, MemoryOrder::ACQ_REL);
int32 old_val2 = __atomic_exchange(&counter, 100, MemoryOrder::SEQ_CST);
// Compare-And-Swap (CAS)
int32 expected = 42;
bool success = __atomic_compare_exchange_strong(
	&counter,
	&expected,   // Updated with actual value on failure
	100,         // Desired value
	MemoryOrder::SEQ_CST,
	MemoryOrder::ACQUIRE // Memory order on failure
);
[/CODE]
### 24.4 Wait and Notify (Futex) Support
To support efficient thread synchronization without busy-waiting, SL provides wait/notify intrinsics. These map directly to OS-level futexes (Linux/Windows) or WebAssembly `memory.atomic.wait` / `memory.atomic.notify`.
[CODE]
// Blocks the thread if the value at ptr equals expected_val
__atomic_wait(&counter, 0, MemoryOrder::SEQ_CST);
// Wakes up 'count' waiting threads (0 wakes all)
__atomic_notify(&counter, 1, MemoryOrder::SEQ_CST);
[/CODE]
### 24.5 Alignment and `packed` Safety Rules
Atomic operations on most hardware architectures (and strictly in WebAssembly) require natural alignment.
**Compiler Rule:** The compiler will emit a hard error if an `atomic` type is placed inside a `__attribute__((packed))` struct (see Section 5.2.1) or if an unaligned pointer is cast to an `atomic*`. This prevents silent data corruption and hardware traps.
### 24.6 WebAssembly Shared Memory Integration
In WebAssembly, atomic instructions are only valid if the linear memory is declared as `shared`. Developers should use the SLP conditional compilation token `WASM_SHARED_MEMORY` (see Section 21.2) to manage target-specific memory allocation and atomic availability.
### 24.7 Interaction with `refclass` and Pointers
- **Atomic Pointers**: `atomic MyClass* ptr;` is fully supported and essential for lock-free data structures.
- **`refclass` Restrictions**: Because `refclass` (Section 20.5) relies on hidden reference counts and automatic memory management, making the *contents* of a `refclass` atomic is dangerous and conflicts with SL's explicit memory philosophy. Atomics are restricted to primitives, enums, and pointers. If thread-safe reference counting is needed, it is handled internally by the `refclass` compiler-generated `retain()`/`release()` thunks using hidden atomic RMW instructions.
### 24.8 Synergy with `defer` and Exception Safety
Atomics integrate seamlessly with SL's `defer` statement (Section 20.4) to ensure exception-safe lock management. This guarantees that locks are released even if a `throwable` function errors out inside a critical section.
[CODE]
atomic int32 lock = 0;
void critical_section() throwable {
	// Spinlock acquisition
	while (__atomic_exchange(&lock, 1, MemoryOrder::ACQUIRE) == 1) {
		__atomic_wait(&lock, 1, MemoryOrder::RELAXED);
	}
	// Guarantee lock release when scope exits (even on throw/error)
	defer {
		__atomic_store(&lock, 0, MemoryOrder::RELEASE);
		__atomic_notify(&lock, 1, MemoryOrder::SEQ_CST);
	}
	// Critical logic here...
	openFile("data.txt"); // If this throws, defer executes automatically
}
[/CODE]

# Software Requirements Specification (SRS)
## Small Language Preprocessor (SLP) Runtime Library

### 1. Introduction
#### 1.1 Purpose
The purpose of this document is to define the functional and non-functional requirements for the Small Language Preprocessor (SLP). SLP is a runtime JavaScript library that interprets and executes a lightweight, JavaScript-like scripting language directly within the host environment. By providing a fast, embedded interpreter, SLP enables dynamic preprocessor-style text generation and logic without a separate build or compilation step.

#### 1.2 Scope
The SLP will be implemented as a pure JavaScript library. It shall parse and execute the custom SLP syntax at runtime. The system supports variable declaration, basic data types (with 64-bit integer support via native BigInt), arithmetic/logical/bitwise operations, control flow, functions, objects, arrays, and lexical scoping, all executed directly by the JavaScript engine.

---

### 2. System Overview
The SLP system consists of two main components:
1. The SLP Interpreter Engine: A JavaScript-based tool that parses and executes SLP script code at runtime. It performs syntax validation, manages lexical scope, and handles execution flow.
2. The JavaScript Host API: The interface exposed to the host application, allowing it to load scripts, persist state across executions, and invoke marked preprocessor tokens directly.

---

### 3. Functional Requirements

#### 3.1 Language Syntax & Lexical Elements
* FR-1.1 Comments: The interpreter shall support single-line comments (//) and multi-line comments (/* ... */) in the source SLP code, ignoring them during parsing and execution.
* FR-1.2 Variable Declaration: Variables shall be declared using the var keyword in the source code (e.g., var x; var x = 123;).
* FR-1.3 Template Literals: The interpreter shall support string interpolation using ${variable} syntax within double-quoted (") or backtick-quoted strings in the source code, resolving them dynamically at runtime.

#### 3.2 Data Types
The interpreter shall support and correctly handle the following data types at runtime:
* FR-2.1 undefined: Represents uninitialized variables.
* FR-2.2 integer: Whole numbers. The interpreter shall utilize JavaScript BigInt to guarantee full 64-bit unsigned integer support without precision loss.
* FR-2.3 float: Floating-point numbers. Mapped to standard JavaScript double-precision numbers.
* FR-2.4 boolean: true or false values.
* FR-2.5 string: 8-bit character sequences, supporting native concatenation and interpolation.
* FR-2.6 array: Ordered lists, supporting native JavaScript array operations.
* FR-2.7 object: Key-value pair collections, supporting native JavaScript object operations.

#### 3.3 Operators
The interpreter shall support and correctly evaluate the following source operators:
* FR-3.1 Arithmetic: +, -, *, /, %, ** (exponentiation), ++, --.
* FR-3.2 Assignment: =, +=, -=, *=, /=, %=, <<=, >>=, &=, ^=, |=.
* FR-3.3 Comparison: ==, !=, >, >=, <, <=.
* FR-3.4 Logical: &&, ||, !.
* FR-3.5 Bitwise: &, |, ^, ~, <<, >>.
* FR-3.6 String: + for concatenation.
* FR-3.7 Conditional: Ternary operator condition ? true_expr : false_expr.

#### 3.4 Control Flow
The interpreter shall correctly execute the following control flow structures:
* FR-4.1 Conditional Statements: if, else if, else, and switch statements.
* FR-4.2 Loops: Standard for loops, for...in loops, while loops, and do...while loops.

#### 3.5 Functions and Scoping
* FR-5.1 Function Definition: Functions defined via arrow syntax (var func = (args) -> { ... }) shall be executed as native JavaScript closures.
* FR-5.2 Arguments Access: Function arguments shall be accessible by name and via a built-in args array in the source.
* FR-5.3 Lexical Scoping: The interpreter shall resolve lexical scopes at runtime, mapping local variables to local execution contexts to avoid global namespace pollution.
* FR-5.4 Return Values: Functions shall use the return keyword, returning values directly to the caller.

#### 3.6 Objects and Arrays
* FR-6.1 Object Literals: Support for declaration, dynamic property assignment, and property access.
* FR-6.2 Array Literals: Support for declaration and initialization.
* FR-6.3 Array Methods: The interpreter shall provide built-in implementations for a.push(value), a.unshift(value), a.pop(), and a.shift().
* FR-6.4 Array Properties: a.length shall return the direct length property.
* FR-6.5 String Methods: The interpreter shall provide highly optimized implementations for str.charAt, str.charCodeAt, str.substring, str.startsWith, str.endsWith, and str.indexOf.

#### 3.7 Preprocessor Directives
* FR-7.1 #token Directive: The source script shall support a #token directive to mark a variable or function as an exported preprocessor entry point.
* FR-7.2 Token Syntax: The interpreter shall recognize both inline declaration and post-declaration marking patterns:
  #token var name = 123;
  #token var namefunc = () -> { return 134; }
  var name = 123; #token name;
* FR-7.3 Token Behavior: The interpreter shall register any variable or function marked with #token in its internal token registry, making them accessible via the `get()` API method.

### 4. JavaScript API Requirements (Library Interface)

#### 4.1 Core Interface
The JavaScript library shall expose an SLP class with the following minimum interface:
* FR-8.1 Initialization: const slp = new SLP(); shall instantiate a new, isolated interpreter instance.
* FR-8.2 Script Definition: slp.define(script: string): DefineResult
  - Shall parse and execute the provided SLP source code at runtime, maintaining global state.
  - Returns a DefineResult object: { success: boolean, tokens: string[], error_message: string }.
  - On success: success is true, tokens contains the string names of newly registered tokens, error_message is "".
  - On failure: success is false, tokens is [], error_message contains a descriptive parse or runtime error string (e.g., "Parse Error: ...").
* FR-8.3 Token Execution: slp.get(token_name: string, ...args: any[]): string
  - Shall evaluate a variable or invoke a function marked with #token.
  - Returns the result as a string, or an error string on failure.

---

### 5. Non-Functional Requirements

* NFR-1 Performance: The system shall provide fast interpretation speed. Parsing and AST traversal shall be highly optimized in pure JavaScript to minimize runtime overhead.
* NFR-2 Error Handling: Parse and runtime errors shall be caught during the define() phase and returned in the DefineResult. The interpreter shall avoid using JavaScript throw statements in hot execution paths, returning error strings instead to maintain performance.
* NFR-3 Memory Management: The interpreter shall manage its state efficiently, relying on the JavaScript garbage collector while avoiding unnecessary object creation in hot execution paths.
* NFR-4 Portability: The library shall be written in vanilla JavaScript, runnable without modification in Node.js or modern browsers.
* NFR-5 Library Implementation Restrictions: The library must strictly adhere to vanilla JavaScript best practices. This includes avoiding eval() for user code (using a custom parser instead), avoiding dynamic hot-path operations where possible, and ensuring no external dependencies are required.

---

### 6. Example Usage (Acceptance Criteria)

The implementation shall successfully execute the following JavaScript code snippet, demonstrating runtime interpretation, state persistence, and direct function execution:

const slp = new SLP();

// 1. Define and execute the initial SLP source code
const defineResult = slp.define(`
    #token var globalmsg = 123;

    var func1 = (x, y) -> {
        return x + " " + y; 
    }
    #token func1;
`);

if (!defineResult.success) {
    console.error("Definition failed:", defineResult.error_message);
} else {
    console.log("Defined successfully. Tokens:", defineResult.tokens);
    
    // 2. Invoke the variable token directly
    const varResult = slp.get("globalmsg");
    // Expected varResult: "123"

    // 3. Invoke the function token directly with arguments
    const result1 = slp.get("func1", 123, 124);
    // Expected result1: "123 124"

    // 4. Define an update to the state (persists across calls)
    const updateResult = slp.define(`
        globalmsg += "hi"; 
        #token var func2 = (a, b, c) -> {
            return "msg: " + globalmsg + ", args: " + a + "," + b + "," + c;
        }
    `);
    
    const result2 = slp.get("func2", 10, 20, 30);
    // Expected result2: "msg: 123hi, args: 10,20,30"
}

### 7. Implementation Restrictions & Testing Guidelines

#### 7.1 Library Implementation Restrictions
The interpreter must guarantee stable, predictable execution. Key rules include:
* Use a custom parser/lexer; do not rely on eval() or new Function() for executing user SLP code.
* No JavaScript exceptions (throw) in the generated/interpreted code hot paths; errors must be returned as string values via the DefineResult or get() methods.
* Maintain strict lexical scoping to prevent variable leakage between unrelated script executions.

#### 7.2 Testing Guidelines (Isolated Execution)
When writing tests for the interpreter, each test case should be scoped using block statements `{ }` in the source code to ensure the interpreter does not carry over invalid state or cause variable name conflicts in the global scope. 

Bad Practice (State Leakage):
  // Test 1
  slp.define(`var x = 123;`);
  // Test 2 (Interpreter will conflict with or overwrite global 'x')
  slp.define(`var x = 456;`);

Best Practice (Isolated Execution Units):
Wrap test definitions in a block { } in the source code, ensuring the interpreter cleanly encapsulates the scope for each test.
  // Good Practice
  const result = slp.define(`{
      var x = 123; 
      var testFunc = () -> { return x; }
      #token testFunc;
  }`);
  // The interpreter will cleanly encapsulate 'x' within the block scope and export only 'testFunc'.
